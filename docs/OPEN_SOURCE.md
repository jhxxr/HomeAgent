# Open Source Repository and Source Releases

**English** · [简体中文](OPEN_SOURCE.zh-CN.md)

This repository releases its original source under the MIT License at version 0.4.19; the npm release is split into two packages, `homeagent-server` and `homeagent-runner`. The Server package contains only the compiled Server, Dashboard and Server assets; the Runner package contains only the Runner, the shared protocol and the Windows process-tree helper. The CLI and source share the same license; both npm packages use file allowlists to include only files needed at runtime, documentation and licenses. Package-name availability and account publish permissions are as determined by the registry at release time.

## File Layout

| Path | Contents |
| --- | --- |
| bin/, src/, public/, runtime/ | CLI, Server, Runner, Dashboard and Windows process-tree helper code |
| tests/ | Tool, security, protocol and Node/Python scenario tests running in temp directories |
| deploy/, Dockerfile, compose.yaml | Self-hosted deployment files |
| scripts/ | Config initialization, backup, license generation, source inventory and release checks |
| docs/ | Deployment, protocol, tools, development workflow, source comparison and validation boundaries |
| licenses/, THIRD_PARTY_NOTICES.md | Locked production dependency licenses and notices |
| .github/ | CI, automatic Release, issue/PR templates and dependency update config |

Every guide under `docs/` is shipped in two languages: the unsuffixed file is the canonical English guide and the `.zh-CN.md` file is the aligned Simplified Chinese translation. Both are part of the release, so the source archive and npm packages include both language versions; the root README also ships as `README.md` and `README.zh-CN.md`.

`.env.example` is the Server config template; Runner connection settings are generated by the `homeagent` interactive UI. Real `.env`, Runner config, device credentials, databases, edit backups, logs, reference source checkouts, `node_modules` and build directories must never enter a release.

## Local Preparation

```sh
npm ci
npm run verify
npm run notices:check
npm audit --omit=dev --audit-level=high
npm run release:npm
npm run test:package
```

`npm run release:check` inspects Git-tracked files and unignored new files, validating sensitive credential patterns, forbidden runtime directories, license/version consistency and local Markdown links. Before committing, use `node scripts/check-release.mjs --staged` to inspect the actual staged content. It never prints the matched secret text.

Only these images are allowed: `public/icon.png` and `docs/screenshots/dashboard.png`, `dashboard-mobile.png`, `permissions.png`, `jobs.png`, `runner-tui.png`; PNG headers are checked and each image is limited to 2 MiB and 4096 pixels per side. Image content still needs human review; screenshots should come from an isolated demo environment and contain no real credentials or private project data. The Runner package carries only the icon used by the README, not the Dashboard scripts.

These are reproducible automated checks only; they cannot prove the absence of unknown kinds of sensitive data. Before publishing, still manually review the file list, deployment examples and private paths. Do not substitute "zip the whole working directory" for a source release.

After updating production dependencies:

```sh
npm ci
npm run notices
npm run notices:check
```

Commit `package-lock.json` and `licenses/npm-runtime.txt`, preserving the original dependency terms. Release scripts and CI do not execute reference repository code.

## Generating a Clean Source Archive

Commit the prepared files to Git and keep the working tree clean:

```sh
npm run release:source
```

Output goes to the ignored `release/`:

- `HomeAgent-v0.4.19-source.tar.gz`
- the corresponding `.sha256` checksum file
- the corresponding `.manifest.txt`, including version, Git commit and all release paths

The archive is generated only from HEAD and contains no `.git` history, Git author config, ignored files, databases, temporary credentials or `node_modules`. Running the command does not create a remote repository, push, tag, upload a Release or publish to npm.

If old Git/runtime data from before the rebuild was kept in a private backup outside the repository, do not upload that directory; it is not part of the project source. Historical validation documents no longer reference commit IDs that exist only in old local history.

## npm Package Checks

`npm run release:npm` builds the JavaScript, packs the two packages separately with `--ignore-scripts`, checks archive file allowlists, runtime assets and SHA-512 integrity, and outputs:

- `release/homeagent-server-0.4.19.tgz`
- `release/homeagent-runner-0.4.19.tgz`
- a `.sha256` for each archive
- `release/npm-packages.json`: both packages' names, versions, Git commit, checksum, dist-tag and path lists

`npm run test:package` installs both archives globally into isolated temp prefixes, verifying the real `homeagent-server` and `homeagent` command shims, help/version, Server config initialization and overwrite refusal, Runner config, plus starting the Server from the installed package, loading Dashboard static assets, Runner login and `/mcp` authentication. Linux and Windows CI both run this check. Nothing is uploaded to npm and the user's existing global installs are not modified.

## Automated Release via GitHub Actions

`.github/workflows/release.yml` supports two entry points:

1. Push a version tag, for example `v0.4.19`.
2. In Actions → release → Run workflow, enter an **already existing** version tag.

Configure `NPM_TOKEN` as described in the next section. After the initial source push, configuring the real `origin` and confirming Actions are available, you can publish as follows:

```sh
# First commit this version's source and docs, keeping the working tree clean
git tag -a v0.4.19 -m "HomeAgent v0.4.19"
git push origin v0.4.19
```

This document is release documentation only; the preparation scripts do not execute these commands for the operator.

The tag must match `package.json`, `package-lock.json` and the runtime VERSION, and `CHANGELOG.md` must have a non-empty entry for that version. A prerelease may use `v0.4.19-rc.1` (all related version files must then be `0.4.19-rc.1`). Do not disguise an ordinary branch or a mismatched version as a release.

The release pipeline runs in order:

- Validate the actual tag, its target commit, version and changelog.
- Call the reusable CI at that exact commit, running Linux/Windows tests, installed-package smoke tests, license/release checks and Docker Compose health verification. CI installs Python explicitly rather than relying on an interpreter happening to be preinstalled in the runner image.
- Generate the source tar.gz via Git archive; build and check both npm tgz files; generate checksums and manifests for all three; take release notes from the current version's changelog.
- The npm publish job downloads the already-verified archives, re-checks commit, package name, version, dist-tag, checksum and remote tag for each, and publishes using a Secret or OIDC. It does not checkout, does not install dependencies, and `npm publish --ignore-scripts` runs no package lifecycle scripts. The Secret is passed only to that publish step.
- Only after npm succeeds does the GitHub Release job receive `contents:write`. That job does not checkout source, run `npm install` or execute project code; it re-checks the remote tag, creates a draft, uploads the source archive, npm packages and metadata, and finally publishes.

The GitHub Release uses the automatically provided `GITHUB_TOKEN`; no GitHub PAT is needed. npm uses the `NPM_TOKEN` described below by default, or OIDC can be configured. Organization/repository policy must allow the Release job to write; protect permission to create version tags. Prerelease tags are automatically marked as GitHub prereleases and use the npm `next` tag, avoiding replacement of the stable `latest`.

An already published GitHub Release for the same tag is never overwritten. If an upload is interrupted, the draft is retained and a rerun for the same tag can complete the assets. If npm succeeded but the GitHub Release failed, a retry skips duplicate npm publishing only when the SHA-512 integrity of that version in the registry exactly matches the verified package; otherwise it fails. Network errors are not treated as "version does not exist". npm versions cannot be overwritten; fix by incrementing the version, never by moving an old tag.

The current release ships source and the npm CLI; it does not upload a Docker registry image or produce standalone EXEs. GitHub workflows only actually run after the repository has been pushed to GitHub and triggered; local preparation does not replace real Actions verification.

## Configuring NPM_TOKEN

1. Log in to the npm website with your own account, enable 2FA and create a **granular access token**.
2. Grant **Read and write** publish permission for the target packages and enable **Bypass 2FA**. A stage-only token cannot perform this workflow's direct `npm publish`. When creating a package for the first time, ensure the token allows creating it; authorizing only another existing package does not grant permission for a new one. After the first publish, narrow it to the target packages, set a sensible expiry and rotate on schedule. Do not use a disabled classic Token.
3. In the GitHub repository → Settings → Secrets and variables → Actions → New repository secret, set the name to **`NPM_TOKEN`** and paste the npm Token value. It is not a Variable and not a GitHub PAT.
4. Leave `NPM_AUTH_MODE` unset (default Token), then push the version tag. Adding the Secret alone does not trigger a release.

The Token is never placed in `.npmrc`, repository files or command output. The first publish creates two public packages; if either name is taken, first change the corresponding manifest and docs, or use an npm scope you control.

**Platform rule date: 2026-10-26.** npm has announced that granular Tokens will lose the ability to directly publish new versions in **January 2027**. The current Token path applies only while direct publishing is still allowed; migrate to the OIDC approach below in advance and do not build long-term automated releasing on a fixed Token. Follow npm's official access tokens / trusted publishers documentation and your account's actual settings.

## Switching to npm OIDC Trusted Publishing

Once the packages exist, add a GitHub Actions trusted publisher in the npm package settings: owner/repository must match the actual public repository, the workflow filename is **`release.yml`**, and leave the GitHub Environment field empty when none is configured. Then add the GitHub Repository Variable **`NPM_AUTH_MODE=oidc`**.

The workflow already grants the npm job `id-token: write`, uses npm OIDC/provenance and removes the Token userconfig; this path does not read `NPM_TOKEN`. After a successful switch you can delete the old Secret and revoke the Token. First-time package creation and account identity verification may still require interactive steps on your own device, as npm requires at the time.

## After Choosing a Hosting Platform

The repository owner creates the public repository, configures the real remote and maintainer contact channel, enables private security reporting and checks Actions permissions. The project does not auto-fill unverifiable remote addresses, auto-configure branch protection or send messages to external parties.

After the first push, observe the actual Linux, Windows and Docker CI results. The current local validation record must not be presented as CI already run on that public repository. Before production use, complete your own HTTPS, backup/restore and system reboot acceptance.
